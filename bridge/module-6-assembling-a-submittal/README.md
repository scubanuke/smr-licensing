# Module 6 — Assembling a Submittal

## Learning Objectives

After this module, a reader will be able to:

- Lay out a review set in tracks and impose a reading order on it that a reviewer can actually follow.
- Distinguish a conformance matrix from a traceability matrix and say what each one makes visible that the other does not.
- Decide what belongs on a public docket and what must be protected, using a stated material test rather than instinct.
- Apply the name-the-gap rule to a requirement the record does not satisfy.

## What this module does

The framework modules taught what a regulator requires. This one is about the difference between a package that is complete and a package that is *reviewable* — a difference that decides how a review actually goes.

The unifying claim is that a submittal is an argument with a load path. A reviewer should be able to start at any provision and walk to the place the record addresses it, and start at any part of the record and walk to the requirement it serves. When both directions work, an orphaned requirement is visible immediately. When neither does, the staff builds the map themselves and charges the applicant for it in review time.

## Units

**[The Three-Track Package](00-the-three-track-package.md)** — orientation and transmittal, core design basis, supporting instruments, and the Reviewer's Guide that imposes the reading order. Which instruments are core because the governing instrument inherits from them, and which are supporting because they are referenced rather than relied upon.

**[Matrices and Anticipated RAIs](01-matrices-and-anticipated-rais.md)** — the conformance matrix maps outward from the record to the regulation; the traceability matrix maps inward from each requirement to the instrument that carries it. Together they are a completeness ledger. Then the anticipated-RAI document: pre-answering the questions a reviewer will ask, including — especially — the pointed ones, because a package that only pre-answers the easy questions has advertised where its trouble is.

**[Classification and the Docket](02-classification-and-the-docket.md)** — the public-record versus protected split, and the mechanism that manages it: class-level instruments stay site-neutral and public, while derivatives accumulate site-specific detail that is designated before docketing. The material test is whether a passage would materially aid an attack on a specific facility, and applying it honestly is harder than stating it.

**[Name the Gap, Name the Vehicle](03-name-the-gap-name-the-vehicle.md)** — the house rule, stated as a rule. Where the record does not conform, the record says so, identifies what would close it, and names who can move it. This is the discipline that makes a package usable on a docket rather than merely advocacy, and it is the reason the register on this site exists as a separate half rather than a footnote.
